# LLMOps Bootcamp — еталонні рішення

Еталони до курсу [llmops-bootcamp](https://github.com/TarasFedorenkoFTV/llmops-bootcamp).
Один бранч = один тиждень: `w1` … `w6` (кумулятивно — кожен наступний містить попередні).

**Цей бранч (`w6`): реалізовано W1–W6** — повний контур + `INCIDENT_RUNBOOK.md` і eval-гейт у CI.

Поріг гейта: `--threshold 9` у `.github/workflows/eval-gate.yml` — датасет має
10 кейсів, 9 = N−1 за правилом ДЗ тижня 5. Розширюєш датасет — оновлюй поріг
у **двох** місцях: локальна команда прогону і workflow.

## Як цим користуватися (студенту)

Спершу — власна спроба, потім звірка. Еталон учить лише після того, як ти сам(-а)
вперся(-лась) у проблему; інакше це просто чужий код у твоєму репозиторії.
Твої ДЗ живуть у **твоєму** репозиторії (див. `GETTING_STARTED.md` §12 крок 0
у публічному стартері) і залишаються тобі після курсу.

Канонічні формулювання завдань і критерії приймання — у публічному репо курсу:
`starter/homework/hw1.md` … `hw6.md`. Тут їх копій немає, щоб не розходилися.

## Запуск

```bash
docker compose up --build     # той самий стек, що у стартері
docker compose -f docker-compose.yml -f demo-ports.yml up --build   # порти зайняті? — зсунуті (UI :4300, service :8180)
```

Ключові місця рішень підписані коментарями `[W1]`, `[W2]`, … у
`service/Program.cs`.

## 30-day rollout (еталонний приклад)

Головний transfer-артефакт ДЗ тижня 6. Формат кожного кроку: практика курсу +
**конкретна дія у своїй команді** («впровадимо evals» — ні; дія з назвою
системи і числом — так). Приклад для команди підтримки:

1. **Тиждень 1 — слід і вартість (самоокупний крок).** Увімкнути unified-лог
   LLM-викликів у нашому support-сервісі: `request_id`, `model`, токени,
   `cost_usd`, `latency_ms`, `prompt_version`. Перший же звіт
   `GROUP BY model` показує, куди йдуть гроші.
2. **Тиждень 2 — промпти під контроль.** Винести системні промпти з коду в
   реєстр із версіями й однією активною; версія їде в лог кожного запиту —
   відкат стає одним `UPDATE`, а не деплоєм.
3. **Тиждень 3 — golden set.** 10 кейсів із реальних тікетів нашого саппорту:
   позитивні + негативні (`forbid` / `expect_refusal`), runner з exit code;
   прогін локально перед кожною зміною промпта.
4. **Тиждень 4 — гейт у CI.** Eval-прогін на кожен PR у support-сервіс,
   required status check; поріг за правилом N−1 (далі — 85% з округленням
   угору). Регресія промпта фізично не мержиться.
